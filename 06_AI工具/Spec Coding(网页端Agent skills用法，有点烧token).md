# 1. Spec Coding 到底是啥？

**直接说结论**：Spec Coding 压根就不允许 AI 瞎猜，核心关注点是“**先设计，再生成**”。它要求你在让 AI 写代码之前，先写好一份详细的“施工图纸”（Spec/文档）。你不再是那个随口提要求的甲方，而是严谨的**架构师**。你把数据结构、接口定义、业务逻辑用文档写得清清楚楚，然后把这堆文档甩给 AI，让它严格按照你的规矩办事。

如果说 Vibe Coding 是“看着感觉对就行”，那 Spec Coding 就是“**必须精准符合文档定义**”。

**Vibe Coding vs. Spec Coding**
- **Vibe Coding**（感觉流）：
    - **核心**：靠直觉和即时反馈。
    - **做法**：随便说一句“给我个贪吃蛇游戏”，AI 写完了你运行看看，不对再改。
    - **适用**：原型开发、简单脚本、或者是你不想动脑子只想看结果的时候。
- **Spec Coding**（规范流）：
    - **核心**：靠文档和上下文约束。
    - **流程**：
        1. **写 Spec**：在你敲第一行代码前，先写 Markdown 文档。定义好：我要用什么技术栈？数据库字段长啥样？API 接口怎么设计？有哪些边界条件？
        2. **喂给 AI**：把这份文档（Context）喂给 AI，告诉它：“读懂这个，别自由发挥，按这个写。”
        3. **生成代码**：AI 变身为一个执行力极强的“高级外包”，它不再猜你想要什么，而是翻译你的文档。
        4. **验收**：由于规则明确，生成的代码通常能直接跑通，甚至连测试用例都给你写好了。

说白了就是，人类负责**顶层设计+编写文档（Spec）**，AI 负责**照单全收+底层搬砖**。这是一种“**谋定而后动**”的高质量生产力，专门解决 AI 写代码容易“写飞了”或者“逻辑不通”的问题。

# 2. Spec Coding 怎么个流程？

**流程逻辑：**
1. **Drafting (起草)**：你打开一个 `.md` 文件（比如 `todo-app-spec.md`），用自然语言+伪代码写下你的需求。
 > _例子：“创建一个 Todo List，前端用 React，状态管理用 Zustand。数据结构包含 id, content, isDone。核心功能需包含……”_
2. **Context Loading (投喂)**：将这个 Spec 文件作为上下文（Context）提供给 AI 工具。
3. **Generation (生成)**：你只需要发一个指令：“**Implement based on spec**（根据文档实现）”。
4. **Review (审查)**：检查代码是否严格遵循了文档。如果不对，你改的不是代码，而是**回去修改 Spec 文档**，然后让 AI 重新生成。
这就像是：**你不是在写代码，你是在写给 AI 看的“说明书”。**
# 3. 工具

Spec Coding 对工具的要求是：**必须能极好地处理上下文（Context）和多文件理解。**

### 1. Cursor (配合 .cursorrules)
这是 Spec Coding 的神器。你可以在项目根目录写一个 `.cursorrules` 文件，把你的 Spec 写进去。Cursor 会在每次生成代码时自动读取这个规则，保证风格统一、逻辑严密。

### 2. VSCode + Cline (或者 Windsurf)
Cline 等插件允许你手动把 `architecture.md` 或 `requirements.md` 钉在聊天窗口里。AI 会时刻盯着这个文件写代码，一旦它“幻觉”了，你就指着文档打它的脸。
### 3. Model 选择
- **Claude 3.5 Sonnet**：目前 Spec Coding 的王者。它的逻辑推理能力极强，非常听话，能完美理解复杂的文档结构。
- **OpenAI o1/o3**：适合写最初那个复杂的 Spec 文档，帮你把脑子里的想法结构化。
